**ATTRIBUTION CORRECTION 2026-10-26 (supersedes the partial findings above).** A bounded objdump re-simulation (../ef-re/snow-blend-equation.txt, raw windows ../ef-re/snow-blend-table-native.txt, full .text ../ef-re/snow-blend-fulltext-native.txt) proved: 0x521b80 is an alpha-keyed whole-pixel copy with zero table references (src alpha OVERWRITES dest alpha on drawn pixels); the three-table description belonged to SCREEN 0x51e4f0. All four lookup tables are runtime-built BSS with no file bytes; initializers were re-simulated exactly (0 of 65536 mismatches): B=trunc(r*c/255), A=255-trunc((255-r)(255-c)/255), C=trunc(k*P/255) with P>=255 filling zeros, D=hardlight-shaped /256.

The four modes: SCREEN 0x51e4f0 (dest alpha preserved), HARDLIGHT 0x51e220, ADDITIVE 0x51dba0 (alpha adds), MULTIPLY-FADE 0x51ded0; blend param P=[record+0x34]. Layer routes 0x522d20/0x521b80/0x523380 contain no table blend; 0x523380 is a /256 fade lerp over all four channels. The actual runtime route for Snow and the writer of +0x34 remain explicit unknowns; a route-evidence followup is in flight. The six decoded ops are ported as tested isolated units in scene.rs (ef_screen_blend_pixel and siblings); production still uses the source-over approximation until the route is pinned.
