# Round 22 — BGM wildcard evidence and acceptance follow-up

No runtime source change this round. Revisited the BGM wildcard parsing question against the exact original ef_first_AA.exe (SHA-256 9824732313d13136cb2300f33038a655ba480ae01cefc2749028d1b1748b4f9e). Bounded objdump traces show the native handler for .playBGM at 0x4ebd60: it has command-specific initializer and parser blocks from 0x4ebc10; the parser retains six required handler arguments and separately parses a seventh optional integer. The fade-in/fade-out, default volume/rate/seek and loop fields are populated before the command reaches audio mixing at 0x4dd5f0. Numeric parameters use native default values when omitted or *; however, I did not prove the global startup defaults or runtime mixer meaning for every field, nor correlate every positional argument with a host-side audio payload. Cold Ghidra import/instruction queries again exceeded the request deadline. Therefore this evidence narrows the bug but is not enough to implement a safe state-preserving fix. No BGM code was changed.

Scripts independently confirm real usage patterns: .playBGM * * 0 (stop with explicit zero in the third argument), .playBGM efBGM013.ogg 0 * (numeric zero fade-in, wildcard fade-out), and .playBGM * 0 9 (wildcard stop parameters). The existing VM still converts unparsable * fields to generic defaults, which can be wrong where native defaults are mutable globals.
