# Round 23 — BGM native defaults and remaining mapping

This round extended the bounded static analysis of the exact original PE (SHA-256 9824732313d13136cb2300f33038a655ba480ae01cefc2749028d1b1748b4f9e). No original binary was executed and no production code changed.

The native handler at 0x4ebd60 rejects fewer than six argument records, then reads the first string and five subsequent parameter records. Static disassembly at 0x436799 writes 0x320 and 0x258 (800 and 600) to globals 0x5dcf30 and 0x5dcf34; the parser at 0x4ebd60/0x4ebd30 uses those as fallbacks for its first two integer fields. Other observed defaults include 0xbb80 (48000) for a later field and 2 for the following field; the boolean field recognizes digits 1-9 and true/T as true, and 0/f/F as false. Additional optional integer fields default to 0. These observations correct last round's uncertainty about the two initialized globals, but their source-level semantic names, full operand index correlation, and native mixer effect are not fully established. The mixer consumer at 0x4dd5f0 operates on several parameter blocks and the repo's AudioHostRequest exposes only loop, volume, pan, fade-in and fade-out, so a complete extension needs verified mapping across the host ABI rather than speculative field insertion.

Extracted original scripts confirm more than 200 BGM wildcard forms, chiefly .playBGM *; also .playBGM * 0 9, .playBGM * * 0, and .playBGM efBGM013.ogg 0 *. The VM still approximates omitted or wildcard numeric values with generic defaults (2/2/100), which is not equivalent to all native fallbacks. A safe targeted implementation remains blocked on identifying which original parameters actually become host fade and volume values, plus state behavior for wildcard track stop; no speculative change was made.
